Замечания к токенизатору/кодировщику LHT/LJS
============================================
(на примере examples/script-basic/binary.dump, token.dump)

Что сейчас работает хорошо
--------------------------
- Контекстно-зависимые таблицы опкодов через COMMAND IMPORT dict=N — один
  байт-опкод переиспользуется в DOM/ATTR/VALUE/LJS/SCRIPT-контекстах.
  Элегантно и расширяемо.
- Builtin-функции (log, alert) как отдельные опкоды — компактно, удобно
  для ROM-зашитого словаря частых имён на retro-таргете.
- START/END вместо {/} унифицирует представление DOM и кода — один цикл
  интерпретатора на оба «дерева».
- Классы литералов (literal:identifier/number/string) + INLINE_VALUE —
  концептуально чисто.

Замечания (что улучшить в выборе пути токенизатора)
---------------------------------------------------
Примечание: половина перечисленного уже поддерживается форматом, просто
токенизатор не выбирает оптимальный путь кодирования.

1) Числа как ASCII — главный проигрыш.
   Сейчас: 100 → 1F + 03 84 03 "100" = 6 байт.
   Рядом DOM-атрибут width=420 кодируется 4 байтами через INLINE_VALUE uint.
   То есть варинт-числа в формате уже есть, но в LJS не используются.
   Кроме размера, это ещё и atoi() на каждом выполнении — двойной проигрыш
   на retro x86.
   Решение: использовать существующие INLINE_BYTE/INLINE_UINT (и аналоги
   для int/float) для LJS-числовых литералов.

2) Идентификаторы переcериализуются на каждом упоминании.
   "outside" встречается ~10 раз — каждый раз 11 байт (1F 03 84 07 "outside")
   ≈ 110 байт на одно имя.
   Решение: локальная таблица символов на скрипт. Первое появление =
   define id N = "outside", далее IDENT_REF N (2 байта). То же для
   повторяющихся строковых литералов ("if-bad" встречается дважды).
   Идея уже укладывается в существующий dict-механизм.

3) INLINE_VALUE слишком толстый префикс для коротких значений.
   03 84 LL <bytes> — байты 03 84 повторяются одинаково перед каждым
   литералом. Имеет смысл «short-string» опкод с длиной <16 в самом опкоде
   (один байт префикса вместо трёх).

4) Слияние «класс + значение» в один шаг.
   Сейчас 1F (literal:identifier) + INLINE_VALUE = два опкода на один
   логический токен. С таблицей символов из п.2 сворачивается в один
   опкод IDENT_REF idx.

5) Полу-токенизация / полу-AST — определиться с линией.
   Формат позиционируется как token stream, но {/} тел if/while
   превращаются в LJS START/END (это уже структура, не лексема), а
   однострочные тела (if (...) log(...);) идут плоско без START/END.
   Стоит выбрать одно из:
   a) честный поток токенов → punct:{/} как обычные пунктуаторы;
   b) мини-AST → все тела обёрнуты в START/END, включая однострочные
      (проще и быстрее цикл выполнения интерпретатора).

6) Читаемость дампа.
   LJS START/END = 01/00, те же байты, что и DOM-START/END. Контекст
   разруливается через COMMAND, но глазами в дампе путается. Не баг,
   просто заметка.

Ожидаемый эффект
----------------
Только пункты (1) varint-числа + (2) per-script symbol/string table
сокращают размер этого примера примерно вдвое и одновременно ускоряют
интерпретатор (вместо atoi — прямое чтение байта; вместо сравнения строк
имени — индекс). Оба изменения ложатся в уже существующую идеологию
словарей формата.
