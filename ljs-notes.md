# LJS — заметки по техдолгу

Обзор архитектуры скриптового слоя (`src/LhtScript.pas`, `src/LhtScriptRuntime.pas`) от 2026-05-19. Многое — осознанные временные решения; этот файл — чтобы не потерять.

Целевая платформа: 386 (flat mode + virtual RAM). 286 — растяжимая цель, не дизайн-драйвер.

## Главное (архитектура)

### 1. Рантайм должен работать с AST, а не парсить токены повторно

Сейчас `LhtScript.pas` строит честный AST через precedence climbing (`ParseEquality/Comparison/Term/Factor/Primary`), а `LhtScriptRuntime.pas` **парсит выражения заново** через `EvalRange → ParseLjsExpressionRange` на каждое вычисление — включая каждую итерацию `while` (`LhtScriptRuntime.pas:679`).

Statement-уровень — аналогично: вместо обхода дерева рантайм сканирует токены через `FindStatementEnd`, `FindBodyEnd`, `FindMatching`. Получается **второй парсер**, частично дублирующий валидатор. Два источника правды о грамматике.

**Целевое решение:** один проход построения полного AST (statements + expressions), интерпретатор обходит только дочерние узлы, без сканов токенов. Это и быстрее, и сокращает код примерно на треть, и автоматически закрывает несколько багов ниже.

### 2. Дублирование грамматики между валидатором и рантаймом

`FindBodyEnd`, `FindMatching`, магические смещения `BodyEnd - 2` (`LhtScriptRuntime.pas:683`) — следствие того, что границы тел заданы token-ranges вместо AST-узлов. Лечится единым AST из пункта 1.

### 3. Строковые префиксы вместо typed tokens

`'kw:' + Word`, `'op:' + S[Pos]`, `'punct:'`, `'builtin:'` — потом весь код пестрит `Pos('kw:', Token.Name) = 1` и `Copy(Token.Name, 4, MaxInt)`. Слабая типизация поверх сильной.

**Целевое решение:** расширить `TLjsTokenKind` (`ljsKeyword`, `ljsOperator`, `ljsPunct`, `ljsBuiltin`) и добавить enum-поля для конкретного значения (`TLjsKeyword = (kwLet, kwIf, ...)`, `TLjsOperator = (opAdd, opEq, ...)`). Сравнения становятся integer-сравнениями, исчезают `Pos`/`Copy` в горячем пути, исчезает аллокация строк в лексере.

## Баги

### 4. `if` с `else` вычисляет условие дважды

`LhtScriptRuntime.pas:699` и `:712` — `EvalRange(ExprStart, ExprEnd)` вызывается оба раза. Если условие имеет побочные эффекты (вызов с `log`), они отработают дважды. Сохранить значение в переменную.

### 5. `ValidateCallStatement` допускает только 1 аргумент

`LhtScriptRuntime.pas:585` (в файле валидатора): `ValidateExpression(Tokens, Index, ')')`. Но `ParsePrimary` парсит вызов с произвольным числом аргументов через запятую. То есть `log(a, b);` пройдёт парсер выражений, но валидатор увидит `,` как неожиданную пунктуацию в `FindExpressionEnd` (`LhtScript.pas:538`). Несогласованность правил.

## Чистка кода

### 6. Дублирование хелперов

`TokenIsDict`, `TokenIsPunct`, `TokenLabel` определены и в `LhtScript.pas`, и в `LhtScriptRuntime.pas`. Вынести в общий internal helper-юнит или экспортировать из `LhtScript`.

### 7. Мелочи

- `ParseLjsScriptText` начинается с `Result := nil; SetLength(Result, 0);` — одно из двух лишнее (`nil` уже даёт длину 0).
- `RequireDict` возвращает `Boolean`, который нигде не используется — лучше `procedure`.

## Соображения, отложенные сознательно

Эти штуки **не делать** в обозримом будущем — для 386 с виртуалкой не критичны:

- **`ShortString` в `TLjsValue` (256 байт на значение).** На 386 копирование быстрое, фрагментации heap нет. String-pool — оптимизация ради оптимизации.
- **`SetLength(..., N + 1)` повсюду.** Под капотом FPC дин. массивы уже растут с capacity, реалокация амортизированная. Норм.
- **`ELjsReturn : Exception` как механизм возврата.** На 386 unwind дёшев. Косметика, не перфоманс.
- **Конкатенация `Result := Result + S[Pos]` в `ReadStringLiteral` / `EscapeStringLiteral`.** Дёргается редко, на коротких строках. Если станет горячим — заменить на `SetLength` + индексное заполнение.
- **Линейный поиск в `FindVar` / `FindFunction`.** Lexical addressing (имена → `(scope, slot)` на этапе парсинга) — красивое решение, но требует уже AST. Имеет смысл делать одновременно с пунктом 1.

## Приоритеты

1. **Единый AST + интерпретатор по узлам.** Закрывает №1, №2, №4; готовит почву для lexical addressing.
2. **Typed tokens (enum вместо строковых префиксов).** Закрывает №3; чистит лексер и сравнения.
3. **Согласовать правила вызова в валидаторе и парсере.** №5 — простой фикс, но требует решения: разрешаем ли несколько аргументов у `log/alert` или ограничиваем парсер.
4. Чистка по №6, №7 — попутно.

### Design rationale: где применяется `START`/`END` (для Slice 4)

**Правило:** `START`/`END` — для тел и других пропускаемых структурных регионов. Скобки выражений `(a+b)*c`, списки аргументов вызова `f(a, b)`, списки параметров `function f(a, b)` — обычная пунктуация (`punct:(`, `punct:,`, `punct:)`).

**Почему `START`/`END` хорошо ложится на тела `if`/`while`/`function`:**

- структурно однородны: внутри тела — те же statements, что и снаружи;
- skim-парсер может пропустить регион целиком, не заглядывая внутрь;
- нет внутренней пунктуации, специфичной для роли тела;
- декодер при канонизации однозначно эмитит `{` / `}`.

**Почему скобки выражений — не тот случай:**

- несут семантику приоритета, а не «вложенный блок такого же сорта»;
- экономия словаря — две записи (`punct:(`, `punct:)`) на весь язык, незаметно;
- декодер при канонизации потерял бы однозначность: `START` сейчас всегда `{`. После расширения нужен либо stateful-декодер, либо kind-discriminator на `START` — что убивает «generic» в идее.

**Почему списки аргументов / параметров — ещё хуже:**

- внутри есть запятые-разделители. Замена `(` на `START` оставляет половину пунктуации списка — никакой однородности;
- альтернатива «каждый аргумент — отдельный `START`/`END`-подблок» убирает запятые, но: пустой список становится «ноль подблоков» вместо естественного «`(` сразу `)`», теряется интуиция «список через запятую», накладные расходы маркеров на каждый вызов.

**Принципиально:** `START`/`END` — это обещание «здесь структурный регион, пропускаемый целиком при skim-парсинге». Сильное свойство бинарного формата. Если этим маркером пометить ещё и скобки выражений и списки — обещание размывается, маркер перестаёт значить «структурный блок» и начинает значить «любое вложение». При работе с потоком (итератор по top-level statements) пропуск `START`/`END` перестаёт давать предсказуемую границу.

**Будущие кандидаты на `START`/`END`:**

- тела `try` / `catch` / `finally`, если появятся — тот же класс, что `if`/`while`;
- module/namespace bodies — если язык дорастёт.

**Будущие НЕ-кандидаты (оставлять punctuation):**

- массивы `[1, 2, 3]` и object literals `{key: val}` — внутри запятые, та же проблема, что у списков аргументов;
- параметры `function f(a, b, c)`.

### Чего не хватает в roadmap

- **Связь со спецификацией.** Roadmap описывает реализацию (`LhtScriptRuntime.pas`, `lhtc runscript`), но ни разу не сослался на Section 9 спеки. Дать якорь.
- **Точка «freeze syntax».** Язык эволюционирует от среза к срезу. Явно сказать: до какого момента грамматика может меняться без deprecation, что делаем когда часть уже зафиксирована в бинарном формате.
